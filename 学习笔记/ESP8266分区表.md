## 1. 分区表是什么

flash 在硬件层面是一条**扁平的地址线**：`0x000000` 到 `0x1FFFFF`，就这么长。
芯片分不出哪一段是代码、哪一段是数据。

分区表就是一张**地图**，告诉 bootloader 和程序：

- 哪一段**是什么**
- **在哪**（Offset）
- **多大**（Size）

它自己放在 flash 的**固定位置** `0x8000`（由 `CONFIG_PARTITION_TABLE_OFFSET` 决定）。

> **为什么位置要固定？**
> 因为 bootloader 上电时**还不知道地图在哪**。这是个鸡生蛋问题——
> 只能硬编码一个约定位置，让所有人去那儿找。

> **为什么要有这张表？**
> 也可以不用分区表，把地址硬写进代码。但那样一旦要挪布局，所有代码都得改。
> 分区表把**"东西放在哪"**和**"代码怎么用"**解耦了（详见 §5）。

## 2. 2MB 长什么样

```
0x000000 ┌──────────────────────────┐
         │  bootloader      32 KiB  │  不在分区表里，固定在这
0x008000 ├──────────────────────────┤
         │  分区表自己       4 KiB  │  上电第一件事就来这儿读地图
0x009000 ├──────────────────────────┤
         │  nvs             16 KiB  │
0x00D000 ├──────────────────────────┤
         │  otadata          8 KiB  │
0x00F000 ├──────────────────────────┤
         │  phy_init         4 KiB  │
0x010000 ├──────────────────────────┤
         │                          │
         │  ota_0          992 KiB  │  固件默认烧在这儿
         │                          │
0x108000 ├──────────────────────────┤
         │                          │
         │  ota_1          992 KiB  │  OTA 写在这儿
         │                          │
0x200000 └──────────────────────────┘  2MB 到头
```

**前 64 KiB 为什么空着？**

```
0x0000 – 0x7FFF   bootloader（32 KiB）
0x8000 – 0x8FFF   分区表自己（3 KiB 内容 + 余量）
0x9000 →          你的分区从这里开始
```

这两块是 ROM 和 SDK 约定的**禁区**，不能动。

## 3. 每个分区是干什么的

| 名字 | 类型 | 干什么 | 谁在用它 |
| --- | --- | --- | --- |
| `nvs` | `data` / `nvs` | **键值存储**，像芯片自带的小 EEPROM | WiFi 驱动存射频校准数据；你也可以用 `nvs_set_str()` 存自己的配置 |
| `otadata` | `data` / `ota` | **OTA 状态记录** | 只记 `ota_seq`，bootloader 靠它决定启动哪个槽（§10） |
| `phy_init` | `data` / `phy` | **WiFi 射频初始化/校准数据** | 每颗芯片射频特性有微小差异，校准一次存这儿，免得每次开机重算 |
| `ota_0` | `app` / `ota_0` | **应用程序槽 0** | 你的 `esp-01S.bin` 就烧在这儿 |
| `ota_1` | `app` / `ota_1` | **应用程序槽 1** | OTA 把新固件写这儿，然后切换过去 |
| ~~`factory`~~ | `app` / `factory` | 出厂固件 | 本仓库**没有**这个分区，原因见 §9 |

## 4. Type 和 SubType

`Type` 只有两大类：

| Type | 含义 |
| --- | --- |
| `app` | 里面放**可执行镜像**。bootloader 挑一个 app 分区，把镜像搬进内存然后跳过去执行 |
| `data` | 放**数据**，CPU 不去执行它。程序自己读写 |

`SubType` 是大类里再分小类，决定**谁在用、怎么用**：

| Type | 可用的 SubType |
| --- | --- |
| `app` | `factory` / `ota_0` / `ota_1` / `test` |
| `data` | `nvs` / `ota`（即 otadata）/ `phy` / `nvs_keys` / `spiffs` / `fat` / `coredump` |

> CSV 里 `Type` 也可以写数字：`app` = `0`，`data` = `1`。
> SDK 自带的 `partitions_two_ota.csv` 就写成 `ota_0, 0, ota_0, ...`，和 `app` 等价。
> 写名字更可读。

## 5. 关键：程序按名字找分区

**这是分区表存在的真正意义。**

看源码里的 `nvs_flash_init()`——它**没有任何地址参数**。
它自己去分区表里找 `subtype = nvs` 的那一块，拿到地址再用。

```c
/* 伪代码，表达意思 */
esp_partition_t *p = esp_partition_find_first(ESP_PARTITION_TYPE_DATA,
                                              ESP_PARTITION_SUBTYPE_DATA_NVS,
                                              NULL);
/* p->offset 和 p->size 都来自分区表 */
```

后果：

- 你把 `nvs` 从 `0x9000` 挪到别处 → **代码一行都不用改** ✅
- 你把 `nvs` 那一行删了 → `nvs_flash_init()` **直接报错**，而不是悄悄写到错误的地方 ✅

> **这就是解耦的价值。** 名字是接口，地址是实现。

## 6. Offset 是位置，Size 是长度

**同一个数值，在不同列里角色不同。**

看这张表（本仓库改造前）——`0x10000` 出现了两次：

```
                          Offset      Size
factory,   app,  factory,  0x10000,   0x1E0000,
ota_0,     app,  ota_0,    0x1F0000,  0x10000,
                             ↑            ↑
                           位置          长度
```

两个 `0x10000`，**数值一样、单位一样（都是字节）**，但：

- 在 **Offset** 列 → "从第 65536 个字节开始"，是个**坐标**
- 在 **Size** 列 → "长 65536 字节"，是个**长度**

**坐标和长度不能互换。** 把 Size 填进 Offset，整张表就乱了。

### 硬性规则

```
这一行的 Offset  =  上一行的 Offset + 上一行 Size
```

这两个数是**手工填的**，算错只有两种后果：

| 错法 | 后果 |
| --- | --- |
| 重叠 | `gen_esp32part.py` **构建时报错** |
| 留洞 | 不报错，但**白扔空间** |

> **最快的自检：最后一行算出来必须正好等于 `0x200000`**（你的 flash 大小）。
> 不等于就说明中间算错了。

## 7. 十六进制 ↔ 大小换算

### 换算只有两步

```
0x10000  = 65536            ← 先把十六进制化成数
         = 65536 字节        ← 分区表规定的单位
         = 65536 ÷ 1024
         = 64 KiB
```

或：`0x10000` = 2^16 字节；除以 2^10（1 KiB）= 2^6 = **64 KiB**。

### ⚠ bit 和 byte 的坑

flash 芯片厂商**经常按 bit 标容量**——因为它内部按位组织、按字节传输。两个数都对，只是单位不同。

ESP-01S 上的 flash 大概率是 **W25Q16**：

```
16 Mbit  ÷ 8  =  2 MByte  =  2 MiB  =  2,097,152 字节  =  0x200000
    ↑             ↑
  型号里的 16     手册另一处写的
```

**是同一个东西。** 所谓"2MB 版本"指的就是 `0x200000`。

### 记住一个锚点就够

| 十六进制 | 字节 | 怎么叫 |
| --- | --- | --- |
| `0x400` | 1024 | 1 KiB |
| `0x1000` | 4096 | **4 KiB —— 一个 flash 扇区** |
| `0x2000` | 8192 | 8 KiB |
| `0x4000` | 16384 | 16 KiB |
| `0x10000` | 65536 | **64 KiB** |
| `0x100000` | 1048576 | **1 MiB** |
| `0x200000` | 2097152 | 2 MiB（整颗 flash） |

只要记住 **`0x1000` = 4 KiB**，往后每多一个十六进制 `0` 就乘 16：

```
0x1000   = 4 KiB
0x10000  = 4 KiB × 16 = 64 KiB
0x100000 = 64 KiB × 16 = 1024 KiB = 1 MiB
```

### KiB 还是 KB

| 写法 | 含义 |
| --- | --- |
| **KiB** | 1024 字节（2^10） |
| **KB** | 1000 字节（十进制） |

日常混着写没人计较，但**地址、分区、扇区**这类地方全是 2 的幂，看到 1024 就该写 KiB。

## 8. 自己排一张表：四步

### 第一步：回答一个问题——要不要 OTA？

这决定有几个 `app` 槽。**这是唯一需要动脑的一步**，剩下三步是算术。

### 第二步：前 64 KiB 是禁区

```
0x0000 – 0x7FFF   bootloader
0x8000 – 0x8FFF   分区表自己
0x9000 →          从这里开始
```

### 第三步：分配，保证首尾相接

每行 `Offset + Size` = 下一行的 `Offset`。

### 第四步：自检

最后一行算出来 == flash 大小（`0x200000`）。

### 例子：算每块 app 槽多大

```
可分配给 app 的空间 = 0x200000 - 0x10000 = 0x1F0000 = 1920 KiB
两个槽对半分        = 0xF8000 每块 = 992 KiB
```

还要**核对固件大小**：

```bash
ls -l build/esp-01S.bin              # 实际镜像大小
xtensa-lx106-elf-size build/esp-01S.elf   # text / data / bss 分解
```

> `esp-01S.bin` 的大小 = `text + data + 91 字节镜像头`。
> 留 **2 倍以上余量**，因为固件会长——本仓库已经从 hello_world 的 167 KiB
> 长到现在的 449 KiB 了。

## 9. OTA 布局怎么选

两种方案：

### 方案甲：`factory` + `ota_0`（**不推荐**）

跑在 factory 上 → 升级写进 `ota_0` → 切过去。

**问题：只能升级一次。** 第二次升级时，它只能返回 `ota_0` 自己——
也就是**要覆盖你正在运行的那块固件**。写一半掉电，砖。

看 `esp_ota_ops.c:614-637` 的实现：

```c
for (t = OTA_0; t != OTA_MAX; t++) {
    p = find_first(APP, t, NULL);
    if (p == NULL) continue;
    if (default_ota == NULL) default_ota = p;   /* 记住找到的第一个 */
    if (p == start_from) next_is_result = true; /* 找到正在跑的那个 */
    else if (next_is_result) return p;          /* 返回它的下一个 */
}
return default_ota;   /* 绕一圈没找到下一个 → 回到第一个 */
```

只有一个 OTA 槽时的执行路径：

```
t = OTA_0 :  p = ota_0
             default_ota = ota_0
             p == start_from   →  next_is_result = true
t = OTA_1..: p == NULL  →  continue
循环结束   →  return default_ota  ==  ota_0   ← 正是你正在跑的那块
```

### 方案乙：`ota_0` + `ota_1`（**推荐，本仓库采用**）

```
跑 ota_0  →  写 ota_1  →  切过去
跑 ota_1  →  写 ota_0  →  切过去
……
```

**永远有一块完整的固件在另一头。**

这也是 SDK 自带 `partitions_two_ota.csv` 的形状——我查过，它就是
`ota_0` + `ota_1`、**没有 factory**。

> Kconfig 里 `PARTITION_TABLE_TWO_OTA` 的说明文字写的是
> "Factory app, two OTA definitions"，那是从 ESP32 抄过来的**过时描述**，
> 和 ESP8266 实际生成的 CSV 对不上。以 CSV 为准。

### 没有 factory 也能启动吗？

能。`bootloader_utility.c:646`，`bootloader_utility_get_selected_boot_partition()`：

```c
if (sa.ota_seq == UINT32_MAX && sb.ota_seq == UINT32_MAX) {   /* otadata 全 0xFF */
    if (bs->factory.offset != 0) {
        ESP_LOGI(TAG, "Defaulting to factory image");
        return FACTORY_INDEX;
    } else {
        ESP_LOGI(TAG, "No factory image, trying OTA 0");
        return 0;                    /* ← 启动 ota_0 */
    }
}
```

空白 otadata（就是烧进去的 `ota_data_initial.bin`）+ 没有 factory → **启动 `ota_0`**。

### 槽位怎么自动轮换

同一个函数往下：

```c
int ota_slot = ota_seq % bs->app_count;   /* 靠 otadata 里的 ota_seq 取模 */
```

`ota_seq` 每次升级 +1，所以槽位**自己就会交替**。你在应用里只需要：

```c
const esp_partition_t *next = esp_ota_get_next_update_partition(NULL);
/* ... esp_ota_begin / esp_ota_write / esp_ota_end 写进去 ... */
esp_ota_set_boot_partition(next);   /* 切换，然后重启 */
```

## 10. 这个 SDK 的 OTA 真相

### ⚠ v3.4 没有自动回滚

证据一，otadata 的结构体（`esp_flash_data_types.h`）：

```c
typedef struct {
    uint32_t ota_seq;
    uint8_t  seq_label[24];
    uint32_t crc;          /* CRC32 of ota_seq field only */
} esp_ota_select_entry_t;
```

**只有 `ota_seq` + `crc`，没有状态位。**

证据二，`esp_ota_ops.h` 里公开的 API 一共这些：

```
esp_ota_begin / esp_ota_write / esp_ota_end
esp_ota_set_boot_partition / esp_ota_get_boot_partition
esp_ota_get_running_partition / esp_ota_get_next_update_partition
esp_ota_get_partition_description
```

**没有 `esp_ota_mark_app_valid_cancel_rollback()`。**

> ESP32 的自动回滚靠 otadata 里的**状态位**（`PENDING_VERIFY` / `VALID` / `INVALID`），
> bootloader 发现状态不对就切回另一块。ESP8266 这套机制**没有**。

### 后果

**新固件起不来 → 无限重启，不会自动切回旧的那块。只能靠串口救回来。**

### 怎么办：自己在应用层做

在 NVS 里存一个启动计数器：

```
每次启动   计数器 +1
连上服务器报到成功   → 计数器清零
启动 N 次都没报到成功 → esp_ota_set_boot_partition(另一块) → 重启
```

这就是"手动版回滚"。等真要写 OTA 时再做。

> **上线前的底线**：每一版固件都先在桌面上验证过。
> 没有自动回滚的平台，这是唯一可靠的保险。

## 11. 格式上的三个坑

改 `partitions_2mb.csv` 时，这三条都是真踩过的：

### 坑 1：必须纯 ASCII

`gen_esp32part.py` 按 ASCII 解码，**一个非 ASCII 字节就让所有构建目标失败**——包括注释里的。

而且它在 **cmake configure 阶段**就被读，不只是 build 阶段。

### 坑 2：最后一个逗号后面不能有东西

```
nvs, data, nvs, 0x9000, 0x4000,      ← 最后这列是 flags
                                       ← 这里写注释会被当成 flag
```

那一列是 `flags`，除了 `encrypted` 之外任何东西都报 `unknown flag`。
**注释要单独占一行、以 `#` 开头。**

### 坑 3：注释也不能有中文

和坑 1 是同一件事，但特别容易忘——因为"注释是人看的"这个直觉在这里不成立。

## 12. 怎么验证

改完分区表，**不要靠肉眼看**。三个命令，不需要板子：

### ① 语法检查和重叠检查

```bash
python $IDF_PATH/components/partition_table/gen_esp32part.py \
       partitions_2mb.csv build/_test.bin

python $IDF_PATH/components/partition_table/gen_esp32part.py \
       --verify build/_test.bin
```

第二条会把解析结果**倒着打印出来**，可以直接核对 Offset 和 Size：

```
nvs,data,nvs,0x9000,16K,
otadata,data,ota,0xd000,8K,
phy_init,data,phy,0xf000,4K,
ota_0,app,ota_0,0x10000,992K,
ota_1,app,ota_1,0x108000,992K,
```

### ② 纯 ASCII 检查

```bash
grep -n '[^ -~	]' partitions_2mb.csv
```

**没有输出 = 纯 ASCII。**

### ③ 构建系统会去哪烧固件

```bash
python $IDF_PATH/components/partition_table/parttool.py \
       --partition-table-file build/_test.bin \
       get_partition_info --partition-boot-default --info offset size
```

输出 `0x10000 0xf8000` —— 这就是 `flasher_args.json` 里 app 的烧录偏移。

> **注意**：`--partition-boot-default` 是**子命令的参数**，必须放在
> `get_partition_info` 后面。放前面会报 `unrecognized arguments`。
> `--info` 只接受 `offset` / `size`，多要字段会 `KeyError`。

## 13. 本仓库当前的表

`partitions_2mb.csv`：

```
# Name,   Type, SubType, Offset,   Size, Flags
nvs,       data, nvs,     0x9000,   0x4000,
otadata,   data, ota,     0xd000,   0x2000,
phy_init,  data, phy,     0xf000,   0x1000,
ota_0,     app,  ota_0,   0x10000,  0xF8000,
ota_1,     app,  ota_1,   0x108000, 0xF8000,
```

首尾相接自检：

```
0x9000   + 0x4000   = 0xD000     ✓
0xD000   + 0x2000   = 0xF000     ✓
0xF000   + 0x1000   = 0x10000    ✓
0x10000  + 0xF8000  = 0x108000   ✓
0x108000 + 0xF8000  = 0x200000   ✓  正好 2MB
```

### 相关配置

`sdkconfig`：

```
CONFIG_ESPTOOLPY_FLASHSIZE_2MB=y
CONFIG_PARTITION_TABLE_CUSTOM=y
CONFIG_PARTITION_TABLE_CUSTOM_FILENAME="partitions_2mb.csv"
CONFIG_PARTITION_TABLE_OFFSET=0x8000
```

> 因为用的是 `CUSTOM`，`CONFIG_PARTITION_TABLE_TWO_OTA` 开不开都不影响
> ——自定义文件永远优先。

### 改动分区表之后

1. **重新 configure** —— 分区表是在 cmake *configure* 阶段读的。删掉 `build/` 重来最保险
2. **建议擦一次 flash**（`erase_flash`）—— 不是必须（所有烧录偏移都没变），
   但旧布局的残留数据会留在新分区里，擦干净省心

### 写 OTA 代码要不要改配置？不要

我一开始以为要在 `main/CMakeLists.txt` 加 `REQUIRES app_update`，**实测下来不用**。

`tools/cmake/build.cmake:157` 确实写着：

```cmake
set(requires_common newlib freertos heap log lwip)
```

`app_update` 不在这个列表里。但这只是**默认值**——`main` 这个组件是特殊的，
它自动拿到**所有**组件的头文件路径和库。

**证据一**（`build/compile_commands.json`）：`main.c` 的编译命令里有
**57 个**组件的 `-I` 路径，其中包括：

```
.../ESP8266_RTOS_SDK/components/app_update/include
.../ESP8266_RTOS_SDK/components/spi_flash/include
```

**证据二**（更直接，在你自己代码里）：`wifi_sta.c` 用了 `esp_event`、
`tcpip_adapter`、`nvs_flash`——**这三个都不在 `requires_common` 里**，
而 `main/CMakeLists.txt` 一行 `REQUIRES` 都没写，固件照样跑得好好的。

所以 `#include "esp_ota_ops.h"` 直接用，什么都不用改。

> **教训**：`requires_common` 是**默认值**，不是**全集**。
> 光看这一行会得出错误结论——我就是这么错的。
> 想知道某个组件能不能用，去看 `compile_commands.json` 里实际的 `-I` 列表，
> 或者干脆编译一次。

## 一页速查

```
分区表 = flash 的地图，放在固定位置 0x8000

地址布局（2MB）：
  0x00000 bootloader 32K  ┐
  0x08000 分区表      4K  ├ 禁区
  0x09000 nvs        16K
  0x0D000 otadata     8K
  0x0F000 phy_init    4K
  0x10000 ota_0     992K  ← 固件默认烧这儿
  0x108000 ota_1    992K
  0x200000 到头

三条规矩：
  1. 每行 offset + size == 下一行 offset
  2. 最后一行 == 0x200000
  3. 纯 ASCII，注释独立成行

换算锚点：
  0x1000 = 4 KiB（一个扇区）
  0x10000 = 64 KiB
  0x100000 = 1 MiB
  0x200000 = 2 MiB

OTA：
  ota_0 + ota_1（A/B），不要 factory
  ⚠ v3.4 没有自动回滚，失败会无限重启
```
